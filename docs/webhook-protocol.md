# Webhook 请求与重复交付处理

TabMail 以 HTTP POST 发送 webhook。接收方应按**可能重复交付**处理：例如接收方已经完成业务操作，但发送方未收到成功响应，后续仍可能重试。请求中的稳定事件 ID 和投递 ID 用于识别这种重复；它们不构成 exactly-once 保证。

## 请求头

| 请求头 | 含义 | 在重试中的行为 |
|---|---|---|
| `Content-Type` | `application/json` | 保持不变 |
| `X-TabMail-Event` | 事件类型 | 保持不变 |
| `X-TabMail-Event-ID` | 服务端创建的事件 UUID | 同一事件的所有目标及其重试共用此值 |
| `X-TabMail-Delivery-ID` | 发往一个目标的投递 UUID | 同一条投递的所有重试保持此值；不同投递分别拥有自己的值 |
| `X-TabMail-Attempt` | 该投递当前的尝试次数 | 重试时变化，不能作为去重键 |
| `X-TabMail-Signature` | 配置 secret 时，对实际请求体字节计算的 HMAC-SHA256 十六进制值 | 保留既有签名规则 |

示例身份头：

```http
X-TabMail-Event-ID: 4e9d6435-e893-44ed-98c1-777af70a92a0
X-TabMail-Delivery-ID: 5824aed2-a43a-41a6-98c7-e033716be2d2
X-TabMail-Attempt: 2
```

新增身份头不修改 JSON 正文、事件类型、公司事件的字段投影、签名格式或重试次数。旧接收方可继续按原签名协议处理请求。

## ID 的来源和生命周期

**绑定持久存储时：** 事件 ID 来自已有 outbox 记录的 `id`；投递 ID 来自已有 webhook delivery 记录的 `id`。扇出后的每一条投递保存其 `event_id`。worker 重新领取或 dispatcher 重建时，HTTP 请求直接使用这两个已保存的值，不重新生成。重复执行同一 outbox 事件的已有扇出逻辑按 `(event_id, url)` 保留现有投递记录。

**未绑定持久存储的直接投递模式：** 一次 `Publish` 在扇出前生成一个事件 UUID，每个目标生成独立的投递 UUID。同一投递的后续尝试复用这两个值。直接模式没有持久队列，因此这些身份值不意味着进程崩溃后能够恢复投递。

再次调用 `Publish` 会创建新事件，即使两次调用的正文完全相同，也分别拥有新的事件 ID。事件 ID 不表示业务命令本身已经实现幂等；也不能用正文摘要替代事件身份。

正常生成的事件和投递均具有非空 UUID。若内部兼容调用提供了缺失的 ID，发送器省略对应身份头，不发送全零 UUID，也不会在每次请求时临时生成一个新 ID。旧版本发送器也可能没有这两个头。接收方不能把缺失值或全零 UUID 当作所有旧请求共同的去重键；应按自己的兼容策略处理。

## 接收方如何选择去重键

多数接收方可使用 **`(可信来源标识, delivery_id)`** 区分一条投递与其重试。可信来源标识应来自接收方的固定配置或认证上下文。若多个 URL 有意执行不同的业务动作，各自的投递 ID 可以保留这种区别。

只有在业务明确要求“同一事件经多个目标到达时也只处理一次”时，才使用 **`(可信来源标识, event_id)`**。否则，按事件 ID 合并不同目标，可能遗漏本来需要分别执行的动作。

推荐的持久处理流程：

1. 校验发送来源、请求体签名和本地业务输入规则。
2. 在数据库事务中尝试登记选定的去重键，并保存事件类型和正文摘要，以便发现同一身份附带不一致内容。
3. 对首次收到的键执行业务写入，并在同一事务中记录已完成；已完成的重复请求直接返回成功。
4. 在持久提交完成后返回 2xx。尚未成功的处理不能提前登记为已完成，否则后续重试会被错误跳过。

如果业务动作发生在事务之外，应结合下游自己的幂等能力处理；单独插入一个“已处理”标记无法证明外部动作与标记同时完成。去重记录的保留时间也应覆盖部署实际允许的重试、恢复和人工补投范围。

## 签名覆盖范围与信任边界

既有签名严格基于**实际请求体字节**，不覆盖新增的身份头或尝试次数。接收方应先按原协议验证正文，并通过经过认证的 HTTPS 或已有的受控网络／接入认证确认发送来源；不能仅因为一个身份头长得像 UUID，就信任或执行请求。

这些身份头帮助识别正常投递过程中的重试，不是独立的身份认证、授权凭证或密码学防重放协议。正文签名通过也不能单独证明新增身份头未被修改。需要对身份头做独立密码学校验的集成，应另外定义双方一致的版本化签名协议；本次改动保留现有接收方的签名兼容性。

## 验证范围与实现入口

相关行为回归使用本地 `httptest` 接收端，覆盖：相同正文的两次直接发布、每次发布的两个目标、失败后的重试、outbox 再次扇出，以及新 dispatcher 对已保存投递的再次处理。回归同时检查原始请求体、原有签名和尝试次数保持一致。

存储链路的这些回归使用现有 fake store，证明发送器透传已保存身份；它们不代替 PostgreSQL 多实例租约、外部接收方事务或生产网络的验收。
