# R5：公司邮箱一致性与可维护性重构设计

> **状态：目标设计，尚未实施或发布。** 2026-09-28 建立，源码规划基线为 `d6d512172fb6b874c3283d9df3f4d56758684a13`。本文件定义一个完整优化版本的方向；唯一活跃任务清单和完成证据入口为 [R5-TODO](R5-TODO.md)。不得把目标文件树、接口或验收目标写成当前已具备的能力。

## 1. 版本目标与边界

R5 的目标不是再堆一层公司功能，而是让公司邮箱已有业务在所有入口遵守同一套授权、版本、内容留存和投递状态规则，并使代码、接口、测试与运行手册能够一起演进。R5 是工程迭代代号，不是 `v5.0.0`；正式版本、标签、镜像、Goose 与发布证据仍遵循 [VERSIONING](../VERSIONING.md)。不移动 R4 检查点，不修改前端私有包版本来冒充产品发布。

本版本包含：权限配置与个人覆盖的安全编辑；正常阅读与恢复读取分离；完整已发送资产；收件/发件留存统一；冻结后离职处置；草稿、附件和模板治理；入站/出站租约和不确定结果；索引、事件和缓存一致性；应用边界整理；实际工作台交互；性能与容量基线；增量迁移及可复现发布验收。

保留 Go、PostgreSQL、现有 Goose、对象存储、逐收件人账本、workqueue 和事务 outbox。坚持模块化单体，不新增平行身份系统、通用工作流引擎、第二个权限引擎、第二套数据库迁移器或消息中间件。不得以“最佳架构”为由先大规模搬目录再补安全语义。

不纳入本版：自研 IMAP/POP、原生客户端、付费 SaaS、多公司组织树扩张、外部 IdP/SSO 全量接入、向量/语义邮件检索、自动审批平台、自研恶意软件扫描引擎。保留清晰接口和部署前提即可，不预埋无调用者的抽象。公网 DNS、发真实邮件、生产迁移与部署是另行授权的操作，不由完成规划或普通代码任务自动触发。

## 3. 必须保持的不变量

| 编号 | 规则 |
|---|---|
| I01 | tenant、主体身份、资源 ID 独立校验。地址、历史提交者、管理角色不替代当前邮箱权利。 |
| I02 | 管理权、read、organize、send_as、模板使用权、恢复例外读取分别判定；organize 不能绕过 read。 |
| I03 | 个人 Key 始终是 Key 主体，只能取其当前有效属主权限与自身 scope 的交集；删除属主不变成无主集成 Key。 |
| I04 | 管理命令在事务内重新读授权；修改、revision 和必要审计/outbox 一起提交。零行更新不是成功。 |
| I05 | 不把未提交字段当成 null，不把空数组误解成继承，不把 false/0 当成“没有输入”。 |
| I06 | 内容可见性由当前 mailbox 权利与内容生命周期共同决定；任务、索引、对象、缓存的存在均不能扩大资格。 |
| I07 | 生命周期不能由普通整理操作延长；删除不抹掉投递/接收幂等证据；派生索引不是原件。 |
| I08 | 入站只有在原件与固定目标持久化后才接受；已接受但未投递的字节必须有受控恢复路径。 |
| I09 | 任务入队、下一跳接受和最终送达含义不同；uncertain 不自动重发、不冒充取消或成功。 |
| I10 | 冻结只禁止访问，不妨碍有权管理员完成资产处置；交接不重新启用旧主体。 |
| I11 | 已发送资产不依赖任务生命周期；BCC 与附件不会因任务清理而丢失，也不会泄露到普通列表/事件。 |
| I12 | 每批新证据绑定具体源码；旧 CI、跳过测试、FakeStore 成功都不能替代真实所需验证。 |

## 5. 关键协议决策

### 5.1 权限编辑

保留既有 effective-permission 读取含义；新增/扩展独立编辑快照，包含原始 profile、原始个人 overrides、来源说明及持久 revision。不得从 effective 值反推 overrides。个人覆盖采用明确字段补丁：缺省保持、null 清除覆盖、false/0/[] 是具体输入；前端只提交脏字段和读取时 revision。若保留完整 PUT，必须强制完整字段集和 revision，不能继续接受不完整对象静默清空。

version 必须是数据库维护的单调值，不能用浏览器时间。删除/重建覆盖项不能让 revision 回到初值而接受旧请求（ABA）；把版本放在稳定的权限状态行或现有主体记录，P1 以增量迁移落实。profile 更新、删除、个人覆盖设置/清除、profile 分配都纳入同一协议。系统/global/tenant profile 的管理范围和受影响成员层级在事务内核对。

域名范围要明确 inherit、all、allowlist、none 的语义；已有 SQL NULL、空数组或拒绝全部的内部表示必须有完整映射与回归。是否采用显式枚举列由 P1 的迁移设计确定，不允许未经映射把历史空数组改成相反的权限。配额 day-boundary 在本版默认保持现有 UTC，集中实现并公开说明，不偷偷改成客户端时区。

### 5.2 回执、正常内容、运维恢复

普通内容资格统一为：有效主体 AND 当前租户 AND 原始邮箱 ID AND 当前域名范围 AND read AND 仍存活的邮箱内容条目。SQL 读取资格与投影必须处于可解释的一致性边界；缓存命中仍检查资格。回执可以按既有明确政策保留最小操作状态，但不携带正文、私密收件人、对象键、令牌或可回显正文的诊断。

旧 `/outbound` 入口要么变成安全回执适配器，要么走同一个内容资格端口；不能各自维护第三套条件。`view_content`、附件元数据、附件字节、EML、重放提交结果和搜索摘要一起检查。未知资格/数据库失败安全拒绝，不能回退为完整 job JSON。

恢复例外读取只允许显式平台运维权限、选定公司、具体资源、有效理由和先成功写入的必要审计；读取范围与普通内容资格分离。普通管理员、历史发送者或能见回执的人不自动获得例外读取权。已向浏览器发送的字节无法撤销，这不允许后续请求继续放行。

### 5.3 长期已发送资产及 BCC

发件内容归发件邮箱，而非队列任务。To/CC/BCC 保存为结构化不可变快照，保留原始类别和可核对摘要；网络 MIME 绝不输出 BCC 头。默认 BCC 属于受控发件内容：仅当前该邮箱的 read 权利、域名范围和存活条目共同允许读取。历史发送者撤权后不能靠提交者身份读取；共享邮箱的当前 reader 具有同一内容政策，交接人在获得当前阅读权后遵守相同政策。此政策需在 UI 与管理说明中明确，不再暗中引入另一套收件人权限。

普通列表、状态回执、SSE、webhook、指标和诊断不得泄露密送地址。状态汇总仍基于完整内部账本计算，不能过滤掉失败的密送后把整封信标成成功。已有 job 的确切 BCC 可回填；已丢失来源的历史资产标记 `legacy_unknown`（拟议状态），不能用空列表声称“当时没有密送”。已有不可变触发器须以新迁移受控扩展，不编辑 00010。

### 5.4 留存、恢复与回收

个人邮箱保持长期保留；共享邮箱有限期限按创建时政策快照确定。普通 trash 给出回收站截止时间，但不能延长既有硬到期时间；有效截止取适用截止中的较早者。restore 清除删除/回收站标记，不清除或后移硬到期时间。到期后普通读取与恢复都拒绝，即使物理清理尚未执行。历史个人邮箱非空到期数据需先按既有豁免规则核对/修正，不能因此新引入批量删除。

物理回收和逻辑可见分离：正文到期可以先停止普通访问，仍被投递/恢复需要的对象继续受保护。草稿 JSON 引用、发送关系、归档关系、入站持有共同保护对象。GC 候选要保证推进，选择后在安全锁/事务边界内复检引用，删除元数据与登记 orphan 清理任务原子提交；对象删除失败可重试。

sealed drafts 和 creation tombstones 不自动过期。本版记录其容量与处置政策，不用清理性能任务悄悄删除证据。任何永久销毁能力必须有独立范围、理由、权限与复核，不纳入普通恢复按钮。

### 5.5 账号冻结与离职资产状态

`is_active` 继续表示访问资格；离职处置状态单独表达。冻结后的员工可成为交接目标，接收人仍必须是有效同公司成员；管理层级、最后管理员和租户边界不放松。新计划绑定当前目标身份/状态/资产指纹，状态或资产变化导致重新预览。

同一计划执行重放返回原回执。不同计划不能对同一次离职重复交接；不能仅删除 inactive 检查而放开重复处置。默认封存私人草稿，transfer_owned/discard 仍要明确选择；正在发送与 uncertain 结果保留原证据，不伪装为 cancelled。新入职/重新启用是否允许必须经过明确状态转换，不能复活历史计划或旧凭据。

### 5.6 事务和并发

每个命令记录锁顺序、授权线性化点、revision 消费点、审计与事件原子范围。先形成实际锁图，处理 tenant/user/mailbox/draft/attachment/job/family 交叉依赖；不能笼统把所有读取重新放回 tenant FOR UPDATE。纯读取、单资源 CAS、多资源管理分别处理，必要锁范围由真实 PostgreSQL 竞争测试证明。

跨数据库与 SMTP 不做虚假的分布式事务。网络尝试前保留 durable uncertainty fence，租约过期或状态提交不明时停止重发；授权撤销只约束新的可控制发送动作，已交给 SMTP 的字节不能召回。连接必须遵守 context、截止时间和资源释放，事务中不等待长网络操作。

## 6. 迁移、兼容与清理原则

仅使用后续 Goose 增量迁移；`00014+` 只是从当前最大版本之后顺序分配的规则，不提前把多个并行 PR 都命名为 00014。每批 schema 变更同时交付适配代码、旧数据映射、空库/升级库/重复启动验证及失败恢复说明。

必需的数据主题：权限 revision 的持久化与重置防护、BCC 完整性/未知状态、离职处置身份、必要的留存/引用/查询索引。能由现有列和安全查询表达的规则不新增重复状态列。回填只依据可证明来源，不覆盖不可变正文；失去来源的数据须显式报告。

采用协调升级而非默认新旧 writer 混跑。R5 必须给出哪些早期安全批次可独立发布，哪些必须同批更新 API/前端/schema。未认证兼容的写入端不能靠 feature flag 重新开放旧权限协议。所有旧入口/重复实现有调用清点、替换任务和退出测试；清理应发生在调用者迁移之后，不保留永久双轨。

## 7. 验证与性能目标

现有 `Makefile`、`.github/workflows/company-p0.yml`、`review-source.yml` 和 `internal/testpg/fixture.go` 是验证起点，不另造一套与 CI 不同的成功定义。真实 DB 用例在没有 DSN 时会 skip；发布检查必须统计必跑名单的实际 pass/skip/missing。脚本字段集合检查不是完整 OpenAPI 类型验证。

分层证据：纯逻辑/属性测试、实际 SQL 及故障注入、真实 HTTP、组件与多窗口测试、shipping standalone 镜像浏览器链路、升级/恢复副本、隔离负载测量、经额外授权的公网投递。每层单独报告，不能拿局部绿灯代替后续层。

拟议测试规模为 S（100 员工/500 邮箱/10 万邮件）、M（1000 员工/5000 邮箱/100 万邮件）、L（1000 万邮件的扩展演练）。它们是合成数据集，不是已认证产品容量。S/M 为本版性能门禁；L 的执行预算和是否作为发布门槛在 P0 固定。记录固定硬件、并发、内容大小、冷热缓存、DB 连接数、SQL 计划、p50/p95/p99、内存和磁盘。

初始候选目标：20 并发下 S/M 常规列表 p95 分别不高于 300/500ms，索引已就绪的 M 集正文查询 p95 不高于 1s；数据与安全条件相同的关键路径相对基线不得无解释恶化超过 10%。这些目标必须在 P0 以实测和容量预算冻结，达不到时明确调整理由并保留原值，不能事后修改脚本掩盖退化。附件字节下载、公网投递延迟不套用普通列表阈值。

## 8. 完成的含义

一个批次完成：任务条件有对应实现/测试，未覆盖项明确，源码/迁移/契约/前端/文档同步，提交与测试树对应，经 review 后才勾选。

R5 代码完成：全部必做任务与迁移/安全/性能/浏览器门禁通过、无待定关键协议或阻塞项、旧重复实现已清退。R5 可发布：再具备恢复演练、容量与运维验收及发布清单。R5 已部署：只能在实际授权并完成部署后记录。三种状态不得混用。
