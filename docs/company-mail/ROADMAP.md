# TabMail 公司邮箱化路线图

基线：`e153631cbcbf03fb5738d3846f4eff1edf39e772`。本轮目标：P0 安全与可靠性；P1/P2 只设计，不提前交付。PR 目标分支 `main`，不直接合并、不部署、不修改 DNS、不向外部地址发送测试邮件。

## 1. 产品边界与不可变约束

公司专用浏览器邮箱的主体是员工和邮箱，不是域名资源。保留既有 Go、PostgreSQL、对象存储、工作队列、MIME/DKIM 基础；不整包合并旧公司分支，不引入另一个迁移器。现阶段仍兼容公共临时邮箱和租户集成账号，但不得将其凭据或域名归属解释为员工个人邮箱授权。

- 员工发件：当前公司、有效员工、精确邮箱、`owner_user_id` 或 `mailbox_grants.can_send`，并保留 `can_send` 能力位。个人 API Key 继承当前有效属主，而不是提升为无主集成账号。
- 邮箱操作：`read` / `organize` / `send_as` 相互分开，整理必须有阅读权；个人邮箱属主有内建权限，共享邮箱显式授权。角色管理权不自动成为正文阅读权。
- 管理员读信：仅在当前租户范围内，正常邮箱授权优先；例外读取须先成功写入审计，否则不返回正文或原文。
- 收信确认：持久化原件和固定目标邮箱 ID 后才接受。每个目标独立恢复，成功标记与消息、配额、必要审计、outbox 原子提交。邮件删除后幂等标记仍保留。地址复用不能重定向历史邮件。
- 发信：提交成功不是最终投递成功；SMTP DATA 已接受后的 QUIT 失败不重发。按域进度只能减少已知成功的重复发送，不构成端到端 exactly-once 保证；确认丢失和状态持久化失败必须明确保留不确定性。
- 留存：零小时是永久保留，使用 SQL NULL；个人邮箱不继承临时套餐 TTL。共享邮箱在 P1 增加明确公司资源标记，不依赖“没有 owner”推断业务用途。
- 升级：保留历史授权，不复用同名但异构表；旧 worker/retention/写入端必须先停止再升级。已有基线不重放，新变更以 Goose 增量迁移应用。

## 2. 归档复用与必要适配

参考 `archive/ingress-operations-console`，公司授权来自 `b323cb26ef54d778f9e5d4f2e7a03924aa6fcbb1`，持久化入站恢复来自 `a60e4f2488840cda7b242719da23d477df5ea671`。复用 `CheckSender` / `CheckMailbox` 的精确授权判定和 `prepareCompanySend` 的调用者→精确地址→grant 绑定；复用 ingress receipt/target、事务投递、fencing、原件校验和原子文件写入设计。

不移植归档自研 `tabmail_schema_migrations`，不在 P0 搬入 company_members/settings/invitations/templates，不搬前端，也不将历史 PR 的测试结果冒充本轮结果。

方案细化：

1. `resolve_error` 可能来自数据库/网络，不能一律永久拒绝；接受前无法确定目标则返回失败，接受后目标变化保留原件等待审查。
2. 台账以 job+固定 mailbox_id 为幂等键，地址只是快照；不可仅用 address UPSERT。完成记录不随用户删信消失。
3. dead 原件保护必须同时覆盖引用检查、定时清理和旧任务升级，不只是移除一个 OnDead 回调。
4. 已发布 baseline 的本次修改仅限移除破坏性 DROP；历史同名 grant 表必须保留并显式处理架构冲突，不能 `CREATE TABLE IF NOT EXISTS` 后假定结构匹配。
5. `delivered_domains` 不能解决远端接受与本地提交之间的原子性；不确定结果需停止自动重发并留下故障证据。完整逐收件人账本留到 P2。

## 3. P0：本轮实施与退出门槛

| 编号 | 范围 | 退出门槛 |
|---|---|---|
| P0-1 | 邮箱 owner 与 grant 数据模型、精确 From 鉴权、个人 API Key、排队任务重新鉴权 | A 冒用 B 被拒；owner/grant 放行；撤销、停用、API Key 删除不静默扩大权限 |
| P0-2 | 读信租户边界、同公司正常授权、required audit | 普通管理员跨租户列表/详情/原文/例外读取均拒绝；审计失败无正文 |
| P0-3 | 固定入站目标、原子投递与幂等标记、DB 租约/fencing、原件保护、原子 spool | 部分失败只恢复未完成目标；原件丢失/损坏可观察；dead 不被 GC 清空；过期 worker 不能提交 |
| P0-4 | DATA/QUIT 语义、按域进度、重试授权复检 | QUIT 失败不重发；已知成功域跳过；未知结果不伪装成功/安全重试 |
| P0-5 | NULL 永久留存、owner 邮箱 TTL 豁免、存量保护 | 0 不立即到期；个人邮箱现有/新信不受短时计划清理；无主临时邮箱仍按显式 TTL |
| P0-6 | 移除 baseline DROP、增量 Goose 迁移、历史兼容 | 新库、已应用 baseline 的库、带历史 grant 的库可验证；历史表不丢失；重复启动不重放 |

测试策略：每项先增加能暴露原缺陷的测试，记录实际红灯结果，再实现并运行绿灯验证；数据库相关故障注入必须在真实 PostgreSQL 运行，不能仅依赖 FakeStore。只将实际执行成功的检查记为通过。

P0 完成不是企业邮箱生产验收完成。没有 P1 员工开通和 grant 管理界面，受保护个人邮箱仍需要受控的预置/迁移；严禁用开放注册代替员工开通。

## 4. P1：公司业务闭环（后续，不在本轮实施）

### P1-A 员工生命周期与管理范围

开通→一次性激活→邮箱/共享授权分配→岗位变更→停用→交接。移植归档 company_members/company_invitations 的成熟逻辑，并适配当前 Goose 与邮箱授权。邀请令牌仅保存哈希、有期限、单次消费；不能用“邀请超级管理员”接口开通员工。

补齐不能操作更高权限对象、不能删除/停用最后一个公司管理员、管理员角色变更并发约束。停用须撤销刷新会话和个人 API Key，处理排队任务与共享授权。公司管理员、部门管理员、员工的管理范围与内容访问范围分开。

验收：同公司入职全流程；重复/过期激活失败；部门管理员不能越权管理；停用后会话、原文、SSE、发信和重试全部受限；邮箱可交接而非删人级联删信。

### P1-B 个人/共享邮箱与权限管理

提供 owner 和 grant 的管理 API/界面、权限预览与变更审计。共享邮箱成为明确的公司资源，有独立长期留存策略，而不是“无 owner = 临时邮箱”。主域名和允许别名由公司管理，员工不能自助把所有域名变成可发身份。

正常使用权、管理权、例外读取权分离；发件地址选择只显示当前可用授权。自动化集成使用独立账号与最小 scope，逐步替代宽泛无主租户 Key；不改变 P0 兼容边界而不做迁移。

验收：个人邮箱与共享邮箱分别授权；read 不隐含 send，send 不隐含 read；撤销后列表/详情/原文/发送一致；操作前后有可追溯审计。

### P1-C 管理员模板治理与受控发送

移植归档 draft/published/retired 版本模型：草稿→服务端校验/预览→不可变发布版本→按邮箱与员工授权使用→最终内容快照与来源记录。变量定义必填、类型、长度；身份变量服务端赋值；用户数据只作为模板数据，不执行模板源。

模板维护权、发布权、使用权、发件身份权相互独立。template_only 在服务端执行，不能靠前端隐藏自由输入绕过。缓存按版本而非可变名称；排队、重试、投递前验证当前策略与原始来源。内容审批只在确实需要时引入，且必须绑定内容摘要。

验收：旧版本可追溯；停用模板后的待发策略明确；变量越界/缺失被拒；模板使用不能解锁其他 From；不能以自由正文绕过限制。

### P1-D 工作台与恢复操作

员工邮箱、公司管理、平台运维分区；去除普通员工对套餐/路由/API Key 的操作依赖。统一会话、缓存作用域和取消旧请求；切换账号清空列表、预览和弹窗。新 UI 显示 queued / accepted-by-next-hop / failed / uncertain，而不是把入队称为送达。

移植归档 reason-required、super-admin-only 入站检查/重试 API，再接恢复界面。只能重试未完成目标；不能修改已接受内容/目标；审计失败回滚；使用检查版本防止过时确认；POST 不自动重放。

验收：管理员开通员工→分配邮箱→员工收信→选授权 From 与模板→查看投递状态；故障原件经审核恢复；两个操作者不能重复提交同一检查快照。

## 5. P2：办公能力与运维验收（后续，不在本轮实施）

| 工作包 | 实施顺序与依赖 | 验收 |
|---|---|---|
| 草稿/会话/附件 | P1 邮箱授权后；草稿乐观版本、Message-ID/In-Reply-To/References；附件对象与邮件授权一致 | 断线草稿恢复；回复/全部回复/转发正确；跨邮箱附件越权拒绝 |
| 搜索/恢复删除 | 明确消息生命周期后；公司范围过滤、软删与垃圾箱保留窗口 | 搜索不泄露无权邮箱；删除可恢复；永久清理保留必要账本 |
| 逐收件人出站账本 | 按域 P0 进度升级，保留既有成功/不确定证据 | RCPT 部分成功、4xx/5xx、退信与 unknown 独立；不重发已知成功目标 |
| 全链事务与事件 | 增量吸收归档 UnitOfWork/mutation 设计，不另建引擎 | 业务变更、必要审计、outbox 原子；消费者幂等；多实例通知可恢复 |
| SSO/MFA/会话安全 | 员工生命周期稳定后 | 敏感操作重新认证、身份撤销生效、恢复管理员有审计 |
| 运维/真实投递 | 联合备份恢复、容量报警、隔离区处置、DNS/SPF/DKIM/DMARC/TLS、退信/恶意内容治理 | 从备份恢复邮箱+原件+授权+队列；验证实际公网收发质量与故障演练 |

浏览器专用首期不要求自研 IMAP/POP 全套协议。无实际需求不叠加多组织 SaaS、付费或复杂审批系统。

## 6. 发布与操作流程

1. 记录部署 commit、Goose 版本、历史迁移表、现有 grant 表结构、队列数和对象存储基线；检查历史归档数据库是否使用独立迁移器。未知历史不能猜测兼容。
2. 联合备份数据库与原件，验证备份可读；停止旧 SMTP、worker、retention 和写入 API。
3. 在隔离数据库验证升级、重复执行和必要数据回填；明确旧待处理任务缺失完成账本时只能保留待审，不自动重放。
4. 统一升级所有角色后再恢复；不能新旧 worker 混跑。监测保留原件容量、失败队列、投递不确定任务。
5. 回退以一致的数据库+对象备份或明确兼容版本为依据，不执行会清除 P0 账本/授权的自动 Down。

## 7. 验证证据

实际本轮执行结果见 `VALIDATION.md`。历史 PR 的绿灯不是本轮证据；没有真实 DB、没有浏览器、没有公网发送的项目必须分别标明。P0 交付后仍须通过 P1 业务验收与 P2 运维发布门槛才能宣称正式公司主邮箱可用。
