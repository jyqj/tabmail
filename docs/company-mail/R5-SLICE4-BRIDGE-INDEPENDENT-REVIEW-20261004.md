## JSON/model fidelity and limits

The 7,290-row author Go model is a lexical gate model, **not a Go JSON decoder or executable command model**. Its four accepted rows include a v3 row without admitted-selection presence; that row is only preliminary bridge acceptance, with full helper rejection/validation still required. The model omits malformed document structure, duplicate keys, case-insensitive Go struct matching, nested source/tool types, decoder errors and executable/file checks. Independent full-text reconstruction and manual inspection establish that the intended lexical checks and argv occur in the actual source, but cannot prove Go syntax, type checking, compilation, decoder execution, exec behavior, OS failure handling or physical command propagation. Brace counts are not syntax proof. No Go tool was invoked.

Go `encoding/json.Unmarshal` does not itself promise strict duplicate-key rejection and permits case-insensitive struct-field matching; unknown keys are ignored. Duplicate fields or alias spellings can therefore differ from the model's single canonical field assumptions, and some such documents may reach the Python validation helper after Go checks. This is not treated as a guarantee of zero helper dispatch. The unchanged helper authenticates the same serialized manifest against the external pin, loads it using duplicate-rejecting `strict_json`, and applies exact Python field/version rules before ordinary observation or consumer dispatch. Independent guarded tests exercised actual descriptor-backed pinned load for duplicate root/nested keys, malformed/trailing JSON, invalid UTF-8, missing/case-variant schema, bool/string/float/exponent/null/nonfinite schema, and v2 selected-field null. These reject. Python accepts whitespace around an integer value, while preserving its type; this is not integer coercion. Wrong byte pins reject even otherwise valid minimal v2 headers. These load controls test header/pin behavior, not a complete runtime manifest.

Direct API selectors require actual integers 2/3; None/bool/float/string/list/dict/unsupported integers reject. Actual v3 header/selected-type checks were exercised with only the admission-envelope lookup mocked. Full v3 envelope authenticity was previously accepted in the frozen runtime/adapter and is preserved byte-for-byte here; it is not freshly qualified by that mock. Explicit `from_environment(..., selected_binding_version=2/3)` overrides an invalid environment selector by design; omission rejects that contamination. The frozen CLI has integer choices with default 2, so Go's explicit argv selector governs validate/launch even if an inherited selector changes. CLI integer parsing can accept alternative integer spellings; the Go environment and Python environment gates themselves remain literal-string strict. No new policy inference or fallback is introduced.

Environment changes between Python's child-environment snapshot and selector resolution, or between Go validation and a later helper reading manifest environment paths, are not made atomic by this plumbing. Existing trusted/quiescent executor and path assumptions remain. Serialized pins plus repeated helper checks detect observed incompatibility; hostile concurrent mutation protection, provenance, ownership cleanup and lifecycle qualification remain separate gates.
