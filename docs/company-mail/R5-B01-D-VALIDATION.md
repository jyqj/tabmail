## 3. 本轮实际生产修复

### 入队：先父租户键，再用户，再附件

`enqueueOutboundJobTx` 在取得其他资源锁之前，先以 `FOR KEY SHARE` 保护已存在的父租户；幂等重放判定之后、附件校验之前，再以 `FOR SHARE` 锁定当前发送者并验证active。原数据库BEFORE用户触发器仍保留，作为直接INSERT的额外防线。

新顺序是：父租户KEY SHARE → 提交幂等锁/既有回执重放 → 发送者SHARE → 附件SHARE → 配额锁 → job/归档/收件人账本/附件pin/审计/草稿消费。没有给所有发送加租户FOR UPDATE，也没有削弱全局管理锁。配额、归档、审计、幂等和草稿消费仍在原事务内；SMTP不进入事务。

父键前置解决用户锁之后再等待租户FK的环；用户锁前置解决先拿附件再等待用户的环。幂等回执命中不创建新发送，保留既有重放语义。此处active检查仍不等于已完成profile/grant/template的完整原子授权，其他阶段任务保留。

### 草稿：读取邮箱权利前取得同邮箱SHARE锁

`SaveMailDraft` 在读取mailbox/grant资格前取得该邮箱的 `FOR SHARE`，并保持到草稿事务结束。公司授权、发送策略和交接修改都更新同一个邮箱revision行，因此形成明确顺序：先开始且持锁的合法保存先结束，撤权再完成；或者撤权先完成，新的保存按新资格拒绝。

这不是撤回已完成的保存，也不是让撤权返回成功后允许旧保存继续提交。草稿仍使用原companyReadTx，不新增全租户排他锁。保护范围仅限这条保存路径与现有邮箱治理写入；FinishAttachment、普通内容读取、旧profile/override修改等没有被本修复自动覆盖。

提前处理的范围和保持不变的约束已写进同一TODO的B01-D记录，不将局部修复冒充整个P1/P3/P4/P5阶段完成。
