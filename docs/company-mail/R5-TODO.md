### 0.1 状态、依赖与记录规则

任务格式：编号与标题；依赖/优先级；具体实施边界；交付位置；验收及测试。模块位置为当前入口或明确标记的拟新增位置，不表示这些新文件已经存在。任务优先级“阻塞”表示本版本完成前必须解决，不表示该任务本身已被确认为生产漏洞。

复选框只表示最终完成：`[ ]` 包括 pending/in_progress/blocked，`[x]` 只用于全部验收通过。进行中/阻塞原因记在执行日志，不使用多个互相矛盾的状态文件。任务 ID 永不重用；拆分添加后缀编号并写依赖，取消任务保留决策与范围变更，不通过删除任务虚增进度。

依赖必须全部关闭后才能开始依赖它的实现；资料阅读与独立测试设计可并行，不预先勾选。表内未显式依赖的同阶段任务可并行，但共享 migration、DTO、事务辅助的 PR 必须指定集成顺序。任何七项审计发现必须通过基线与修复后对照关闭；若当前源码已变化，先记录原基线到新 SHA 的映射。

每个完成项在文末执行日志登记：任务 ID、PR/commit、被测 SHA/树、实际命令、测试总数/pass/fail/skip、结果证据路径、兼容变化、未覆盖边界。日志没有凭据、邮件正文、真实个人信息或可用激活链接。测试名称只是要求，不是结果。

### 0.2 全局完成标准

实现必须同时满足：授权/租户边界；空值/false/0/空数组协议；版本和并发；错误路径与审计回滚；前后端一致；迁移和旧数据；观察指标；正常和失败回归。相关项确实不适用时写明理由。不得用放宽权限、忽略错误、跳过 DB 用例、删除原测试或依赖“管理员总是可信”解决红灯。

每批先增加能暴露基线缺口的用例，再修复并跑相关绿灯，最后执行该批完整门禁。纯结构性重构用行为等价证明；风险排查未发现缺陷的任务可用明确测试/证据关闭，不制造无意义代码差异。

## 3. 建议分批实施与 PR 边界

以下 B01–B25 是实施/评审批次，不是承诺工期，也不等于每个批次都能独立部署。一个批次可以拆成明确依赖的多个小 PR；相同协议变更的 backend/schema/frontend 必须在启用前一起完成。B02 只准备协议和迁移，不先启用缺前端适配的新写入接口；B03 才接通完整写入与编辑流程。其他阶段遵循相同规则。

默认依序执行；满足明确依赖后可并行准备独立领域的测试。共享 schema/DTO/事务辅助只能由一个当前批次持有修改权。每次用户说“继续”，先读取本文件执行控制台与最新仓库状态，只领取下一组依赖已完成的任务；不要重新执行已关闭任务，也不要只增加审计报告而不推进本批交付。

| 批次 | 精确任务范围 | 交付主题 | 最低局部门禁 |
|---|---|---|---|
| B01 | P0-010–120 | 实施基线、七项失败复现、验证与基准 | 环境实测、必跑名单、失败原因分类 |
| B02 | P1-010–040 | 权限编辑协议、事务端口和持久revision | 类型/解码/迁移/越权；尚不单独启用新写入口 |
| B03 | P1-050–110 | 权限CAS写入、profile分配及完整编辑器 | 真实PG/HTTP/组件：局部更新、陈旧表单 |
| B04 | P1-120–140 | 权限竞争、审计与阶段收口 | G1，A01/A02闭环 |
| B05 | P2-010–090 | 内容资格、恢复边界、BCC schema与归档 | 权限矩阵、升级/未知来源、归档原子性 |
| B06 | P2-100–150 | 详情/回执/附件/缓存适配与完整资产 | G2，A03/A07闭环 |
