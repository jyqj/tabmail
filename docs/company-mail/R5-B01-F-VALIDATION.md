## 2. 先复现，再修复

在未修改业务代码的开始版本上执行10项新测试，完整结果为 **8通过、2目标失败、0跳过，Go退出1**。两处目标断言分别是：

- `R5_RESERVE_DEFECT_REVOKED`：预留已经读取共享邮箱发送权，随后等待上传者额度锁；真实SetWorkGrant已撤去发送能力并提交，旧Reserve仍新增预留记录。
- `R5_RESERVE_DEFECT_ORDER`：预留等待父邮箱时已经持有上传者额度锁，说明邮箱授权锁没有前置。

它们是同一授权/锁顺序问题的两个观测，不包装成两个独立漏洞。控制器只持有数据库锁以选择时序，授权、额度计算和INSERT仍调用生产实现。失败必须来自具名断言，不接受DB不可用、编译失败或超时替代。原始完整日志SHA-256为 `ba5d29964078fb96da7d5f0a376960943604b05be00dc391d9c529011725b8fb`；对应测试源码随证据保留。

## 3. 新顺序与不变的政策

```text
当前用户SHARE / 身份重验
  → 同邮箱SHARE
  → 当前mailbox/grant发送资格
  → attachment-budget:tenant:user advisory
  → 原有额度计算
  → 预留INSERT
  → 提交
```

管理写入更新同一邮箱revision行，因此只有两种安全先后关系：已获锁的合法预留先提交，撤权随后完成；或撤权先完成，预留读取新资格并被拒绝。撤权完成后的新请求必须拒绝。没有给全部上传加tenant FOR UPDATE，没有移除个人额度锁，也没有改变200 MiB窗口、附件大小或原件保存政策。

此锁不覆盖旧permission profile/override修改，不代表已经交付P1权限原子协议。预留记录仍只是上传过程中的保留，不等于对象Put成功或附件ready；Finish边界继续由B01-E实现约束。

GC的tenant锁与普通草稿/上传不是共同的第一把锁。实际保护包含附件行锁、SKIP LOCKED和删除前引用复检，源码旧注释已据实际调用关系修正。整个Sweep并非单一事务；本批证明的是附件删除与orphan登记的局部原子性。A06的保护前缀饥饿和21租户公平性没有在此修改。
