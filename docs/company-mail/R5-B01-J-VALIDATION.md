## 2. 取得了什么基线失败

| 场景 | 原基线实际结果 | 候选实际结果 |
|---|---|---|
| 完成等job锁后租约到期 | COMPLETE_WAIT目标失败：旧完成仍提交 | Conflict；原job/token/document保留，新token可恢复 |
| 失败等job锁后租约到期 | FAIL_WAIT目标失败：旧失败仍改变任务 | Conflict；不写旧失败状态，保留可恢复任务 |
| 完成等document锁后租约到期 | DOCUMENT_WAIT目标失败：旧正文及完成状态仍提交 | 派生正文与任务一起回滚，新token可恢复 |
| 来源message与job锁次序 | SOURCE_ORDER目标失败：等来源父行时已持有job子行 | 等来源父行时job仍可由NOWAIT探针取得 |

四项均实际run→fail且只出现一次对应 `R5_INDEX_DEFECT_*` 标记，基线Go进程exit=1，其余六项通过且无skip。候选同十项均run→pass、包成功、Go exit=0；没有编译错误、setup错误或超时充当目标失败。

这里是**三种超期写入场景和一个锁序观察**，不是四个独立安全漏洞，也没有把单侧锁探针声称为完整40P01死锁复现。原逻辑把now()事务时间当作等待后的有效性、过早消费租约；候选按来源SHARE→job UPDATE锁→新语句实际时钟→派生写入→最终租约条件更新处理。失败路径只锁job并用实际时间重验，保持固定粗粒度诊断。

对照用例还验证了文档约束失败的原子回滚、取消释放锁、来源替换与旧token拒绝。三项普通读取测试确认：缓存/原件仍存在时，撤去read后的新请求被拒绝且不打开对象；管理员或错误邮箱/租户不能获得正文；等身份锁期间冻结的用户不能信任旧actor。这些读取规则在基线上也成立，本轮没有杜撰新的读取权限修复。对象适配器为计数内存实现，数据库和应用服务为真实实现；不是HTTP、浏览器或S3耐久性验收，不召回已发字节。

数据库时间与锁语义已对照PostgreSQL 16官方[时间函数](https://www.postgresql.org/docs/16/functions-datetime.html)和[显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)；结论以本轮真实测试为据，不以文档替代复现。
