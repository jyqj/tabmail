# 公司邮件治理（预览）

跟踪：Issue #4；实现与验收：PR #5，`feat/enterprise-mail-governance`。
本阶段交付公司身份、邮箱授权与受控模板发送的闭环，不等于完整企业邮局或生产就绪。
主分支不被自动合并，任何真实部署、DNS 修改、启用公司模式均需部署管理员自行执行。

## 业务边界

底层一个 tenant 对应一家公司，保留租户隔离。公司启用后只有一个已验证主域名。
域名不是员工的权限范围：员工被明确授予具体邮箱的 read、organize、send 权限。
个人邮箱与共享邮箱都属于公司；开通员工时建立个人邮箱与本人授权，共享邮箱通过同一授权表分配多人。
目前没有独立的个人/共享类型字段、别名、通讯组或部门树。

| 预设角色 | 能力 |
| --- | --- |
| 公司负责人 | 首次启用者；任免管理员；不能通过日常写信冒用未获授权地址 |
| 公司管理员 | 开通员工、分配邮箱、编辑/发布模板；不能自己给自己加读信或代发权限（负责人例外） |
| 普通员工 `employee` | 使用明确授予的邮箱；可普通写信或用模板 |
| 模板受限员工 `restricted` | 必须使用已发布且绑定到该发件邮箱的模板 |
| 只读员工 `viewer` | 仅查看明确授予的邮箱；不能整理或发送 |

负责人是公司配置里的身份，不是第五个可随意分配的角色。仅负责人能管理管理员；不能停用/降级负责人或自己。
本阶段不提供负责人转移或恢复入口，不应删除负责人；这属于后续需双重验证的恢复流程。
公司成员、邮箱授权、模板版本都保存同租户外键约束。`organize` 必须伴随 read，send 与 read 相互独立。
修改角色不自动扩大已有邮箱授权；将受限员工改为普通员工后，旧的 template_only 授权仍需明确调整。

## 首次部署与启用

先在隔离测试环境验证，不要直接切换承载真实邮件的实例。按现有部署文档设置数据库、Redis、对象存储、JWT/邮箱密钥和 TLS。
所有进程角色应使用一致配置（以下是环境变量，不是完整部署文件）：

```dotenv
TABMAIL_WEBHOOK_URLS=
TABMAIL_MAILBOXNAMING=full
TABMAIL_STRIPPLUSTAG=false
TABMAIL_HTTP_PUBLIC_IPRPM=60
TABMAIL_OUTBOUND_ENABLED=true
TABMAIL_OUTBOUND_MODE=relay
TABMAIL_OUTBOUND_RELAY_HOST=your-approved-relay.example
TABMAIL_OUTBOUND_RELAY_PORT=587
TABMAIL_OUTBOUND_RELAY_TLS=starttls
```

旧的实例级静态 Webhook 会外发邮件元数据，公司模式要求先清空 `TABMAIL_WEBHOOK_URLS`，避免沿用未纳入公司授权的接收方；启用接口及后续启动均会检查。同实例其他 legacy 租户的静态 Webhook 也需停用，或迁至独立实例。

凭据从部署环境或 Secret 管理注入，不写入仓库。配置主域名的 DNS/MX 与发件认证；本次代码测试未进行真实公网投递。
生产建议显式配置 DKIM 必须签名，并验证发件中继、SPF、DKIM、DMARC 和实际送达。`201` 只表示入队，不是收件人已收到。
仅 API 角色不会自行投递，应运行 worker 或 all 角色。公网 SMTP 接收不是员工客户端的 SMTP AUTH 提交服务；本阶段发送入口是网页/HTTP。

管理员在现有域名控制台配置**恰好一个**已完成所有权及 MX 验证的域名。
仍有其他域名或子域邮箱时，启用接口拒绝操作；不能通过直接删除旧业务资产来凑数，应另做数据迁移。
首次启用使用 `/company` 页面，或 `POST /api/v1/company`，必须显式提交 `confirm_lockdown=true`。

### 启用前必须备份、停止旧并发业务

备份数据库和对象存储，并验证能恢复。先停止发件 worker、retention 和旧写入入口，再在维护窗口启用。
不能在旧二进制仍运行的混合部署里启用：旧 Worker 不认识新授权、旧清理器不认识 retention_exempt。
迁移数据库应由部署流程先执行或由一个新实例先完成，再一致升级所有角色。

启用事务执行如下收紧：

- 当前操作者成为负责人/公司管理员；其他现有用户成为 viewer，旧 admin/super_admin 角色被降为 user，避免遗留平台权限绕过。
- 域名不再公开，关闭随机子域和自动创建邮箱；公司域名的未知地址不自动建箱。
- 旧邮箱关闭 public/token 访问；旧的 mailbox token 即使未过期也不能访问公司邮箱。
- 撤销公司旧 API Keys；公司 API Key 请求及旧资源管理写接口不再接受。服务账号待下一阶段设计。
- 旧 pending/retry/processing 发件任务阻断，不能以缺失公司提交凭据的旧任务重试。
- 存量邮件设置 retention_exempt，新公司收件通过数据库触发器获得相同保护。未启用公司的临时邮箱保留策略不变。
- 旧邮箱不自动分配，负责人也不因域名所有权获得正文/发件权限。
- 关闭实例级公开注册和旧平台邀请接受入口（影响同实例其他租户）。员工使用公司专属激活流程。

这里的保留只是**不按临时邮件 TTL 自动清理**，不是合规归档、法律保全或备份。拥有 organize 权限的人仍可调用旧邮件删除/清空 API，删除是物理删除；回收站、恢复、保留期限治理尚未实现。

## 日常操作

1. 负责人打开 `/company`，创建员工，选择角色和每日提交配额。系统原子创建待激活账号、公司地址、本人邮箱授权与激活码。
2. 通过已确认的安全渠道给该员工发送激活码；本阶段**不会自动发邀请邮件**。页面仅在当前操作中显示并允许复制，数据库只存哈希，72 小时过期。
3. 员工在 `/activate` 输入激活码与 12–72 UTF-8 字节密码，激活后正常登录。激活不会创建新租户，也不会自动登录。
4. 未激活账号可以重新发码，旧码立即失效；激活过的账号不能借此重置密码。
5. 共享邮箱先创建地址，再选员工授予 read/organize/send/template_only。旧邮箱通过同样方式明确交接；不得按字符串相似推断归属。
6. 管理员的登录邮箱可能是公司域外的部署账号。需要自己发信时，应先创建主域名下的邮箱，再由负责人明确授予相应 read/send 权限。
7. 员工登录后跳转 `/mail`。可阅读授权邮箱、选择授权发件身份、普通写信或填写模板变量、查看本人发件任务。无权限的管理入口隐藏；后端仍是权威边界。
8. 停用员工撤销刷新会话和旧密钥、使现有 JWT 请求失效，并阻断其未发任务；不删除历史邮件。重新启用恢复原有授权，转岗/交接需要管理员先调整授权。

SSE 每次推送和每次心跳重新核对当前员工/邮箱权限；撤权后不再输出新事件，空闲连接最长等到下一次 25 秒心跳关闭。
已开始的 SMTP 事务不可能保证撤回，投递前复核只能阻止尚未进入传输的任务。不要把停用操作描述为“召回已发送邮件”。

## 模板与发送

管理员在 `/company` 的模板页创建 draft。正文支持纯文本/HTML 与 `{{.customer_name}}` 一类标量变量。
变量定义为名称到最大字符数（1–4000）的映射，最多 32 项；所有声明变量都必填。
`{{.employee_name}}`、`{{.company_name}}` 从当前会话/公司配置填入，客户端不能覆写。
不允许条件、循环、函数、模板包含或任意代码；渲染时即限制展开大小，HTML 进行上下文转义与清理。

每次保存产生不可变版本，`family_id` 表示同一模板系列。只能 draft→published/retired、published→retired。
退役的版本不可重新发布；可以复制内容创建新版本。**模板可用性不会自动授予发件身份。**
管理员可预览草稿，但实际发送仍需 published 版本与 send 授权。

```json
{
  "from": "sales@company.example",
  "to": ["customer@example.test"],
  "template_id": "<已发布版本 UUID>",
  "variables": { "customer_name": "客户姓名" }
}
```

向原 `/api/v1/send` 提交模板发送时不要携带 subject/text_body/html_body；由服务端生成最终内容。
普通员工的自由发件则不传 template_id/variables，并提供主题与正文。公司模式不支持自定义 headers 或 API Key 发件。
同一服务进行身份检查、渲染、验证，再将配额占用、邮件任务、内容/收件人哈希、模板版本和审计一次性提交。
配额按 **UTC 自然日的提交任务数**计，包含管理员，范围 1–10000；不是按收件人数或成功投递量计，重试已有任务不另计新提交。
Worker 和重试接口再次检查当前账号、精确邮箱授权、模板发布状态与内容哈希。退役版本将阻断依赖它的未发任务。

本阶段没有发件审批、草稿自动保存、回复线程、发件附件、通讯录或模板可视化拖拽编辑器。
收件工作台已有正文查看；完整附件下载/回复流及个人已读状态还需独立实现。

## 数据库迁移

`postgres.New` 调用带事务级 advisory lock 的迁移器，`tabmail_schema_migrations` 保存版本、校验和与应用时间。
版本 1 是冻结后的 `schema.sql`；版本 2 为 `migrations/0002_company.sql`。迁移不是每次启动都执行一遍当前快照。
校验和改变或数据库版本高于二进制支持版本时拒绝启动。后续改表应新增版本，不能修改已发布版本。
首次迁移可接纳本分支审计的 main 基线数据库；不宣称兼容任意历史分支的 schema。
历史 grants 表不会被启动脚本 DROP，但旧授权数据不会自动变成公司授权。
不提供自动降级脚本：回退业务必须先评估数据/凭据变化并从经过验证的备份恢复，不能直接跑旧版本。

## 已知生产缺口

部门范围的主管、审批、SSO/MFA、服务账号、负责人恢复/转移；企业密码重置；邮箱别名与通讯组；草稿/回复/附件；每收件人收发恢复和重试幂等；跨进程实时消息总线；对象清理竞态/引用协调；事务 outbox 完整覆盖；备份恢复、投递信誉及容量实测。
旧收发传输中仍存在部分收件人失败不能完整恢复的问题，不能用本阶段权限测试宣称“不丢不重”。
当前 Web 会话仍沿用 localStorage JWT/刷新令牌，迁移到受保护 Cookie 或统一身份登录也是后续加固项。

PR #3 的事务/outbox 改造有不同基线。本分支未隐式合并它，只在公司变更/发送的边界内实现严格事务审计；整站 legacy 写链路不宣称已统一。
